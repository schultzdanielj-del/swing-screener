What's changed about the refinement grinder from the existing spec:

The existing REFINEMENT_GRINDER.md describes a CLUSTER-AWARE mechanic where each cluster
has a rightmost bar (the "real" signal) and leftward bars (predecessor bars, sacrificial).
A loser CLUSTER is eliminated only when ALL its bars fail at least one condition.
Winner-cluster leftward bars are also expendable.

Under the L14 labeler era, the unit is the INDIVIDUAL DOUBLE-SIGNAL (per-firing,
pre-dedup). Each row is one double-signal that fired both pyramid + presignal. The
labeler attaches WIN or LOSS to each row independently. There is no run-collapsing.

Refinement's job in plain language (Dan 2026-04-26): "take the winner pile of double
signal entries and the loser pile of double signal entries. find ways to carve out more
losing double signal entries without sacrificing winner pile double signal entries. it
can sacrifice a combination of the pyramid grind signals that are either duplicates or
non double signals in the process. it needs strong logic so that it's able to provide
benefit without huge curve fit issues. so the job of it is to essentially work on the
win/loss piles and increase win rate without overfit."

Translated to spec terms:

  Winner pile  = ENTRY-tagged clusters with final_label == "WIN" (examples + wild WINs).
                 Per-row, no rightmost/leftward distinction. Winners must all pass.
  Loser pile   = ENTRY-tagged clusters with final_label == "LOSS". Per-row.
                 Carve as many as possible.
  Sacrificable = the live-scan pool (pyramid signals not in the labeled double-signal
                 pool, plus any signals that are deduplicates of labeled rows in some
                 setup-aware sense). Refinement conditions may eliminate these as
                 collateral with no penalty.

Open design questions for this session (these are what to engage with — not pick-one
options, derive answers from data):

1. **Bounding-box semantics under per-signal piles.** Existing spec uses exact
   min/max of winner expression values across all winners (no margin) as the
   bounding box, and conditions are "[low, high] bands per expression." Under
   per-signal piles with 111-218 winners (vs the old ~30-50 example winners),
   the bounding box is wider. How does that affect carve power and curve-fit
   risk? The §3.4 SVD effective rank diagnostic from PRESIGNAL_GRINDER.md
   should transfer — measure it on the new winner pile to see how many
   genuinely independent constraints exist.

2. **Loser elimination semantics.** Existing spec: cluster eliminated iff
   every bar in cluster fails some condition (cluster-conservative). Per-
   signal: eliminate iff the row's expression value falls outside [low, high]
   on some condition. Simpler. But loses the cluster-conservatism that
   prevented coincidental single-bar eliminations from killing whole runs.
   Question: does any of the cluster-conservatism transfer meaningfully to
   per-signal piles, or is the simpler semantics correct?

3. **Curve-fit defense.** Existing spec has two-test validation (consensus
   stability across 50%-loser subsamples + per-condition binomial significance
   against universe baseline). Per-signal piles should still use both tests
   but the implementation details shift:
     - Subsampling: which rows? 50% of loser rows per run.
     - Binomial test: universe baseline computed per expression as before;
       loser exclusion rate is now per-row (not per-cluster-bar). The
       statistical test is the same shape.
   Carry both tests over with implementation adjustments.

4. **Sacrificable pool boundary.** "Pyramid-only signals" (pyramid fired but
   presignal didn't) and "duplicates" are sacrificable. How is "duplicate"
   defined here — same ticker on consecutive bars? Same setup-instance? This
   affects what gets eliminated as collateral and what stays. Ground in the
   data: look at the per-ticker double-signal density, identify natural
   "instances" and "duplicates."

5. **What input format does refinement read?** The current refinement reads
   raw_signal_clusters_*.json (cluster-aware schema). Under L14, refinement
   reads signal_exit_pool_{setup}.json (per-cluster, per-signal labels). The
   schema shift means the load path needs rewriting. Decide: rewrite
   refinement to read signal_exit_pool directly, OR add a translation layer
   that produces a per-signal raw_signal_clusters-like format. The first is
   cleaner; the second is less invasive to existing code.
